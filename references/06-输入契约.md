# 输入契约与填表说明

用 `harness.py init` 建立完整字段结构，再修改。字段名固定英文，内容中文。`validate`仅检查结构；`review`还检查快照哈希、引用文本、有效期、适用版本、支持对象和来源性质。

## 顶层

0.2.0新增schema_version=1.1，必须给review_object（product/development_plan）。CLI默认生成1.1；既有1.0仅用于产品。development_plan另有plan对象、PJ/PF/PA评分、validation/development阶段；产品保持原J/F/A及阶段。`examples/development-plan-empty.json`是可validate的空方案，关键内容为空会被review如实阻断。

新证据须标`review_object=development_plan/product/shared`。方案证据再填`plan_version`与plan.version相等，product_version填目标产品版本；已有产品证据填其真实版本（方案可在baseline_product_version声明一个已有基线）。shared仅用于确实共有的source/rights/cost原件，不接受测试、用户或交易记录。产品路径拒绝标记为development_plan的证据，方案路径的existing卖点只接收product证据。

schema 1.1的共享对象和共享版本必须同时标shared；任何schema中的测试/用户/交易等版本敏感证据都不得使用product_version=shared。旧档案若使用这个绕过路径将被限制，其原始冻结报告仍保留。

plan字段为version、baseline_product_version、scope_in/out、requested_milestone、assumptions、dependencies、milestones、stop_conditions、phase_coverage。结构以模板和 [方案制度](09-开发方案评审.md) 为准；空值待补，不填写虚假的默认人名/日期。

方案报告的next_experiment从请求里程碑、关键假设、停止线和budget派生，避免输入中两份计划互相矛盾；兼容字段next_experiment仍保留，但不会覆盖plan的决定范围。

假设证据supports绑定`assumption:<ID>`；依赖绑定`dependency:<ID>`；阶段不适用依据绑定`phase:validation/development/operation/exit`；成本行仍绑定BOM。方案claims增加claim_scope=planned/existing；planned只能是候选假设，提交supported会被降级并形成证据门槛。方案BOM行增加phase，budget增加scope=milestone:<requested_milestone>。

方案数组的每一行字段如下；字段齐全但事实未知时，按指定方式留空：

| 数组 | 必填字段与取值 |
|---|---|
| assumptions | id、kind（demand/feasibility/economics/rights）、statement、critical（布尔）、status（unknown/supported/refuted）、validation（未知用空字符串）、evidence_refs（数组） |
| dependencies | id、description、critical（布尔）、status（available/unverified/unavailable）、owner（未知null）、fallback（未知空字符串）、evidence_refs |
| milestones | id、title、owner（未知null）、due（YYYY-MM-DD或null）、depends_on（里程碑ID数组）、deliverable、acceptance（method/pass/fail/evidence_required四个字符串）、stop_conditions、validates_assumptions（假设ID数组）、resolves_dependencies（依赖ID数组）、bom_line_ids |
| phase_coverage各阶段 | status（included/not_applicable/unknown）、reason、evidence_refs；键为validation/development/operation/exit |

scope_in/out与全局stop_conditions都是文字数组；未知用空数组。requested_milestone须为现有ID或null；null时budget.scope也为null，报告会要求补齐。开发/验证成本basis必须one_off或sunk；sunk不得绑定增量里程碑。结构不允许的字段或悬空/循环依赖会在validate报错，而事实缺失会在review保留unknown。

产品旧档案`schema_version=1.0`；`as_of`显式填写评审日期；`purpose`为live_review、retrospective或synthetic。后两种不会获得现实资源资格。产品`stage`为discovery/pilot/launch/scale；`product.profile`为skill/bot/agent/course/hardware/research（方案也保留这个产品类型）。

product包含id、name、version、profile、lifecycle、user、buyer、job、alternative。id保持稳定；version精确到发布版本或内容哈希；lifecycle为active/paused/closed。修改生命周期不能绕过历史决定，评审者必须核对拥有该状态的实际项目记录。

## 证据记录示例

```json
{
  "id": "E01",
  "path": "evidence/product-01-trial.txt",
  "sha256": "实际文件SHA256",
  "quote": "从快照逐字复制的关键原文",
  "locator": "原件路径/URL及行号、页码或时间范围",
  "product_version": "1.0.0",
  "observed_on": "2026-11-11",
  "valid_days": 30,
  "kind": "test_run",
  "strength": "observed",
  "provenance": "direct",
  "independence_group": "experiment-01",
  "supports": ["F1", "G_CORE", "review:engineering"],
  "semantic_status": "checked",
  "reviewer": "核查者与记录编号"
}
```

示例中的日期/期限是格式示范；有效期需按内容变化速度设定。quote是定位用关键摘录，不能替代审阅完整适用上下文。`shared`仅用于确实跨版本适用的规则或原件，不能给旧版本测试套shared。当前程序验证内容包含引用，不自动判断该句能否支持所有指标；逐项supports由评审者负责任地填写。

`kind`允许source、test_run、raw_data、customer、transaction、human_review、rights、cost、counterevidence。`provenance`：direct是直接取得的原始观察，attested是历史报告/转述，synthetic是合成。文件本身读到，不等于文件描述的测试已由本轮直接观察。历史QA应记attested，最多2分。

`strength`为documented/observed/replicated，对应最高2/3/4分；top score仍需至少两个独立来源组。`semantic_status=checked`必须有实际核查行为；unreviewed/conflicted不会供给分数。声明“checked”不是真实身份签名，首版需人工抽查和只读原件管理。

## 评分、门槛、评议和卖点

ratings必须完整包含15个指标，每项score为0—4整数或null、reason非空、evidence_refs引用现有ID。gates只使用当前类型的合法ID；status为met/not_met/unknown，不允许提交者自行设置not_applicable绕过硬门槛。

五类reviews为engineering/domain/aesthetic/human_acceptance/real_world，每项status、reviewer_kind、reason和evidence_refs必填。人工认可passed只接受human；其他评议也必须有类型适当的证据，若缺失则降为not_run。上线和扩张的必要评议不接受提交者自行豁免。

claims每项包含id、text、proof_kind、status、boundary、evidence_refs、counterevidence_refs。商业/实际效果卖点需要对应真实证据，不能用功能测试证明。反证存在时不能继续把该卖点列为supported。

每层layer_findings包含value/problems/next_action。初评可以明确写“未发现足够证据支持价值”，不能为了格式完整而编造价值。

## 成本行

```json
{
  "id": "model-inference",
  "category": "inference",
  "basis": "per_unit",
  "status": "estimated",
  "unit": "一次完整交付",
  "reason": "根据任务调用日志估计；含重试；现金报价来源另附",
  "quantity": {"low": 1, "base": 1, "high": 1},
  "per_quantity": {
    "cash": {"low": null, "base": null, "high": null},
    "owner_hours": {"low": null, "base": null, "high": null},
    "team_hours": {"low": null, "base": null, "high": null},
    "tokens": {"low": null, "base": null, "high": null},
    "relationship_uses": {"low": null, "base": null, "high": null}
  },
  "evidence_refs": []
}
```

每类资源都显式填数或null。把单位定义清楚后，再填数量和单价，避免把“一次调用”与“一份完整成果”混用。BOM支持关系使用计数，具体对象与风险在reason/关系台账展开。

`bom.monthly_units`、`price_per_unit`、`horizon_months`定义核算场景。`budget.caps`适用于同一窗口，status为unset/proposed/confirmed；confirmed需引用支持BUDGET的人类确认记录。确认额度并不批准当前具体支出。

## 校准记录

`calibration/human-ratings.json`保存数组，每行包含case_id、trial_id、model、prompt_version、policy_version、human_label_ref、human_gate、ai_gate、human_score、ai_score。gate为pass/fail，分值为0—4。使用独立案例与试次ID；复制行不会增加样本量。

整体评分与逐项评分需保留不同口径。当前统计器针对输入整体锚点评分，详细指标分歧在原始评审表保存。不能将未知门槛强行标为pass；作为不具备放行资格的样本保留原因。
