# 一次评审怎么做

> 0.3.0适用边界：下文实测强度与产品门槛用于产品验收。PRD按[方案制度](09-开发方案评审.md)评设计质量，原始文档可支撑0—4；实证成熟度、执行准备和资源资格另列。未知价格/用量不自动扣设计分，漏成本构成/估算方法仍是缺陷。

## 开发方案

1. 读09-开发方案评审.md及prompts/plan-reviewer.md，固定方案版本、目标产品版本、候选用户和指定下一里程碑。
2. `python harness.py init --review-object development_plan --id 方案ID --name 名称 --profile agent --as-of 2026-11-12 --out intake/新文件.json`。新建模板额度全部null，先填事实和估计，不造审批。
3. 从原文提取候选卖点、假设/依赖、四阶段BOM、各步责任设计/顺序/交付/验收/停止/成本。两阶段都允许未知假设，须有可执行的验证安排；development不要求先有产品试用。关键假设已有适用事实证据另记加分，缺证仅+0，不阻断方案。人名/日历可待定，执行准备另查。不要把评审建议回填成原方案已有设计。
4. 分别记录方案文档、已有产品或共有来源证据；新证据填review_object，方案证据再填plan_version。运行validate与review，检查PJ/PF/PA、生成的里程碑/依赖门槛和当前里程碑资源账。
5. 计划通过后仍只是指定里程碑候选资格；后续有实际结果再建product档案或修订方案。不把方案分复制为产品分；暂停/结项状态不自动改变。

## 新产品或课程

1. 读取README、总制度、对应三层制度和资源口径。固定产品版本及阶段，不默认全部走上线标准。
2. 用init创建档案。只读对象项目；补齐用户、买方、任务、现实替代及已有生命周期。
3. 先读原始材料；把必要原件或有出处的摘录保存在evidence下，填写哈希、适用版本、日期、定位、性质和支持对象。实际查看专业/审美产物；仅有文档不能代替看产物。
4. 按prompts/reviewer.md给每项评分提案和三层价值/问题。成本不知道就填null，同时写需要记录哪一笔调用、哪段工时或哪个报价。
5. 运行validate与review；检查引用失败、分数被压低、未知门槛和成本缺项。修复输入事实错误后写新run，不覆盖旧报告。
6. 输出一句结论、三层卡、可支持卖点、BOM及最小下一步。只有新增且必要的人类事实才向用户提问；已给授权不反复确认。

## 历史项目

purpose设retrospective，product.version固定历史版本。旧报告按attested计，查到原始记录再说明是否可直接支持；本轮没重跑就不能写新运行。已结项/暂停状态照录，试评不等于重启。

## 调参

复制policy为新版本 → 记录原因和具体案例 → 用相同输入运行旧/新参数 → 检查变化、错误放行和边界案例 → 冻结验证集复核 → 用户决定是否采用。只有真正发生的人工评议才记录human。

## 输入输出示例

```powershell
python harness.py init --id course-02 --name "新课程" --profile course --as-of 2026-11-11 --out intake/course-02.json
# 补充证据、成本和评分；这一步包含实际语义审阅
python harness.py review --input intake/course-02.json --out reports/course-02-r1
python tools/verify_bundle.py reports/course-02-r1/task-bundle.json
```

模板中的空值是待补事实，不是要求先完成所有未知才能开始写报告。真正依赖额度的资源判断保持未定，其余工作继续。
